# 本项目实验执行约定

## 后续 Codex 执行模型（2026-11-18）

- 本项目后续规划、执行和经授权的派发统一使用 GPT-6.2 Sol High（`gpt-6.2-sol` / `high`）。这条设置适用于新会话和已有会话的后续执行，优先于旧任务卡中的模型要求。
- 项目默认值见 `.codex/config.toml`。手动转交时选择同一模型和推理强度。保留已完成运行的模型记录与临床推理配置。

## 派发通道（硬性）

- 跨会话派发一律用 `codex-dispatch`：`new` 建会话、`send` 追加一轮，`status <dispatch-id>` 取回执。
  禁止再调用 `create_thread` / `send_message_to_thread` / `fork_thread` / `handoff_thread`：它们走 `http://127.0.0.1:<随机端口>/mcp`，端口随桌面端重启漂移，且会话创建时会把当时的端点固化进上下文，一旦 app 重启该会话就永久指向死端口，表现为 `Transport send error` 且无 threadId 回执。
- 2026-11-20 增加逐任务显式选择 `--backend workbuddy` 的工程入口，固定 DeepSeek V4.1 Flash，限已授权外发的自含任务卡。WorkBuddy 用 `workbuddy.completed` 和退出 0 核验，项目当前只通过合成冒烟。正式使用前先取得真实合成卡的模型与结束回执。见 `discussion/WORKBUDDY_DISPATCH_20261120.md`。
- `codex-dispatch` 默认通过本机 Codex app-server 的固定 Unix 控制套接字派发，直接由桌面端使用的服务接续已有会话。另有显式 `--backend exec` 用于无桌面 daemon 的独立 CLI 运行。操作、回执与安装位置见 `discussion/DISPATCH_CHANNEL_20261117.md`。
- 派发必须留回执：只有日志出现 `{"type":"turn.completed",...}` 才算送达；仅有 `thread.started` 只代表会话已建立，不代表任务已完成。未拿到 `turn.completed` 不得声称已派发/已启动。
- `new` 和 `send` 必须给 `--cd`。默认后端创建会话时设置标题并加入桌面置顶；`read <thread-id>` 可读取会话历史与 Goal，且不会开启模型轮次。
- 派发内容用 `--prompt-file <卡片路径>` 传，不要塞进 `--prompt` 参数，保证任务卡原文可回查。
- 每项待派发任务在 `discussion/CURRENT.md` 顶部列明任务编号和名称、接收会话、唯一入口卡及预计交付文件。已有会话写明标题和 thread ID，新会话写明拟用标题。注明入口是新任务卡还是接续卡，并将历史任务卡、参考报告和验收产物标为查阅材料。实际派发状态单列，按回执更新。
- 用户授权本轮设置独立 Goal 时，可同时用 `--goal-file <路径>` 交付原生 Goal，通过 `read` 查阅状态；派发轮结束与 Goal 完成分别核对。既有未完成 Goal 保持独立，不自动替换。
- 同一条 thread 同时只允许一个 `send` 在跑；上一个 dispatch 未到 `turn.completed` 前不重复派发，避免两个写入者抢同一 rollout。
- 默认后端遇目标会话正在运行会等待前一轮结束后再追加。显式 `--backend exec` 遇 `already has an active writer` 时改走默认后端；默认后端如提示同一会话仍被其他进程持有，核对失败回执及当前执行者再决定，禁止删锁、抢写或盲目重投。
- 不手工写入`session_index.jsonl`制造侧边栏条目；本机实测追加无效且会被app维护。CLI新会话按dispatch-id/status/log管理，侧边栏可见性不作为成功回执。
- 2026-11-18用户授权P01-G1A特例：原主会话无未完成turn后改用独立`new`，该专用执行会话为本阶段唯一生产代码写入者，原主会话保持等待；A02仅只读。此特例优先于下文“本轮不新建/原主会话承担”的旧调度，不扩大到其他任务。
